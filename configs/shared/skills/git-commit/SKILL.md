# Git 提交规范

## 提交前

1. 阅读仓库 `AGENTS.md`、commitlint 配置和最近的提交，优先遵循已有约定。
2. 用 `git status --short`、`git diff`、`git diff --cached` 确认工作区与暂存区的实际变化；留意未跟踪文件，不漏掉本次新增文件。
3. 只处理本次任务的改动，不覆盖或提交他人的无关修改。多个独立主题建议拆分，不为凑数量拆开一个完整改动。
4. 检查冲突标记、敏感信息与明显的格式问题，如实说明相关测试结果；未执行的检查不能写成通过。

## 提交信息

```text
type(scope): 简短描述

可选正文：说明原因、影响或迁移要求

可选 footer：Issue 引用或 BREAKING CHANGE
```

- `type` 使用 `feat`、`fix`、`docs`、`style`、`refactor`、`perf`、`test`、`build`、`ci`、`chore`、`revert`。
- `scope` 可选，仅在模块边界明确时填写；优先使用项目已有范围。
- 默认使用简体中文描述，动词开头、简短具体、句尾不加句号；用户或仓库另有语言约定时遵循其约定。
- 一行能说清就不加正文；不兼容变更使用 `!` 或 `BREAKING CHANGE:`，说明必要迁移步骤。
- 不虚构 Issue 关联，不自动关闭任务，不附加无关署名或模型元信息。

例如：`feat(auth): 新增登录验证码校验`、`fix(api): 修复分页参数为空时的异常`。

## 执行边界

- 用户只要求提交信息时，只输出可复制的 message。只有明确要求提交或推送时才执行相应操作，提交授权不等于推送授权。
- 提交时用 `git add -- <具体路径>` 暂存本次改动，检查暂存区后再提交；不要把无关文件一起加入。
- 推送前确认当前分支和上游，执行 `git fetch` 检查远程进展。需要同步时优先快进，或在工作区干净且只涉及未发布的本地提交时 rebase。
- 出现冲突、无上游、脏工作区影响同步或需要改写已发布历史时，先说明情况并确认处理方案；不自动 stash、丢弃修改或盲选 ours/theirs。
- 普通 push，不强推；不自动 squash、amend、打 tag、发布版本、启动 Review 或安装 Git hooks。
