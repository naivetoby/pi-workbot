# 技术架构

## 组件职责

| 组件                        | 职责                                                   |
| --------------------------- | ------------------------------------------------------ |
| Pi `1.5.2`                  | 模型调用、工具、插件、Skills、MCP、会话和设置          |
| pi-channels `0.1.38`        | 飞书、企微连接，消息队列、附件和会话命令               |
| pi-web `0.17.0`（定制补丁） | 浏览器交互、会话查看、设置和终端                       |
| GitLab / glab               | 需求 Issue、项目仓库、MR、Pipeline 和执行记录          |
| Workbot                     | 环境打包、工作区初始化、渠道启动、Web 启停和 code 派发 |

```text
飞书 / 企业微信                          浏览器
       │                                   │
       ▼                                   ▼
┌────────────────── chat 容器 ─────────────────────┐
│ 渠道宿主 → pi-channels bridge → 业务 Pi           │
│                                   pi-web（按需）│
│          共用 Pi 配置、会话和项目文件             │
└──────────────────────┬───────────────────────────┘
                       │ dispatch_code / glab
                       ▼
          控制项目 Issue + code Pipeline
                       │
                       ▼
┌────────────────── code Job ──────────────────────┐
│ 独立工作区 → 准备任务分支 → 一个 Pi 非交互会话    │
│ 修改 1–10 个项目 → 推送分支与 MR → 回写 Issue     │
└──────────────────────────────────────────────────┘
```

## 镜像与初始化

`Dockerfile` 和 CI 使用 `pi-workbot-dev:latest` 研发底座，默认底座为 `naivetoby/pi-workbot-dev:latest`，通过 `WORKBOT_BASE_IMAGE` 覆盖；CI 工具镜像通过 `WORKBOT_CI_IMAGE` 指定，默认 `docker:cli`。底座基于 Dev Containers Base 与官方 Features，提供 Node.js、Python、Java、Bun、glab、语言服务器和检查器；角色使用 `vscode` 用户，Java 由 SDKMAN 管理。

本项目按锁文件安装 Workbot 与角色插件，提供共享程序、项目清单和 `configs/shared/`。`code`、`chat-assets` 构建层分别禁网验证角色实际使用的 Pi/lens；chat 成品组合 `chat-assets` 的角色资源和 `tui-check` 的 Web/终端产物。CI 发布的角色镜像按提交 SHA 标记。上述构建测试在 CI 中执行，[独立部署](../deploy/README.md) 跳过测试。

业务项目管理依赖、专用 SDK 和构建测试命令，运行环境管理凭证、资源配额、会话卷与缓存。验收按通用工具、角色集成和真实业务任务分层执行。

`src/runtime/init.ts` 负责：

1. 创建 Pi 目录和工作区。
2. 首次复制角色配置，再从共享目录补缺。
3. 为 chat 加入协作扩展和 bridge 启动入口。
4. 校验完整项目清单后再克隆仓库，生成工作区项目说明。

初始化标记保存在 Pi 目录。后续启动保留现有设置，已有项目副本继续使用。新容器从镜像配置初始化；项目克隆时使用清单中的 `branch` 或 GitLab 默认分支。

## chat 与 IM 会话

`src/chat/host.ts` 创建内存中的 Pi SDK 宿主，与 pi-channels 共用配置解析入口，按完整环境凭证筛选 IM 渠道。全部启用渠道就绪后写入 `/runtime/healthy`，Compose 通过该文件探测健康状态；无 IM 时仅检查宿主初始化。

原生 bridge 经 `bin/pi-bridge` 调用 `src/chat/bridge.ts` 启动业务 Pi。适配入口让业务进程按原生文件加载模型、工具、插件、Skills、MCP 和工作约定，同时通过环境设置将渠道连接保留在宿主中。

pi-channels 管理会话队列：每个私聊独立，同群成员共享上下文，不同渠道和聊天的上下文相互隔离。宿主、业务 Pi 与 Web 默认会话均使用 `WORKBOT_WORKSPACE` 指定的工作区（容器中为 `/workspace`），会话在 Web 侧栏归入该工作区。IM 会话文件名包含 adapter 和聊天身份指纹，续接和 `/new`（或 `/clear`）只影响对应聊天。

```text
/runtime/pi/
├── settings.json、models.json、mcp.json、extensions/、skills/ …
└── sessions/
    ├── im/             # 所有 IM 原始会话
    └── --workspace--/  # Web 原始会话
```

IM 会话以原始 JSONL 格式保存在 Pi 的 `sessions/im/` 目录（默认 `/runtime/pi/sessions/im/`），由 bridge 直接写入、Web 统一读取。会话工作目录仍为 `/workspace`，其中不存放会话记录，也不创建会话软链接。容器重建后，可从持久化的 `chat-sessions` 卷接续会话。

`/new` 和 `/clear` 由渠道层调用同一个 reset 流程：取消当前任务、等待子进程退出、丢弃排队消息并删除当前聊天的会话文件，收到下一条消息时创建新会话。`/clear` 不再转发给业务 Pi 的插件命令，避免触发 pi-cc-extensions 会话替换后遗留回调访问旧 ctx 的问题；该规避不修复插件在 TUI/Web 等其他入口的生命周期缺陷。

首次启动业务 Pi 前，bridge 原子写入会话头和首条 `workbot.origin` 自定义条目，记录 `kind: im`、adapter 和 Pi session ID，无需等待模型回复。若初始化写盘失败，则按普通执行错误向用户回复，并释放队列，避免阻塞后续消息。来源标记与 session ID 绑定，因此在 Web 中分叉出的会话不会继承原会话的 IM 归属。

各会话共享项目文件，编辑和提交时需相互协调。

## 按需 Web

`src/chat/web.ts` 用 Bun 启动 pi-web 的 Next.js 生产服务，通过 PID 文件管理进程，日志写入 `/runtime/web.log`。chat 退出时关闭 Web 子进程。

Web 与业务 Pi 使用同一个 `PI_CODING_AGENT_DIR`，支持查看会话、接续 Web 自建会话、修改设置及运行终端。会话列表（含首屏摘要）、详情和在线 SDK 信息均从 `workbot.origin` 读取来源，不根据目录、标题或消息正文推断。IM 会话仅供查看，并提示用户回到对应渠道回复；独立 TUI 启动接口拒绝启动 IM 会话，通用会话 API 的访问权限不变。

配置变化按 Pi/Web 的加载机制生效，现有会话保留自身的模型选择。Web 操作与会话使用约定见 [使用说明](使用.md#按需使用-web)。

开启 `WORKBOT_TUI_ENABLED=1` 时，`src/chat/web-server.ts` 管理 Caddy、Next 和 ttyd。Caddy 使用原公开端口，Next/ttyd 仅监听回环地址；`/tui/*` 页面和 WebSocket 握手先经过 pi-web 认证及 Host/Origin 校验。未配置 Web 密码时拒绝启用。

启动 TUI 前，pi-web 解析会话文件和工作目录，检查 GUI 空闲并释放 SDK。`src/chat/tui-launch.ts` 读取当前运行环境后以 `execve` 启动 `pi --session <文件>`，不传 GUI 工具预设、不覆盖 Pi 原生工具恢复规则。仅此入口加载 `tui-session.ts`，通过 Pi 事件阻止跨会话切换及分叉，避免 tmux 名称与实际会话错配。

GUI 直接查询 tmux 状态决定是否显示只读记录，不维护第二套状态。ttyd 只连接已有 tmux 会话，由 tmux 重绘；Pi 是 pane 主进程，退出即结束该会话。停止 Web 不杀 tmux，也不提供跨进程写锁。依赖、环境交接与合并前验收见 [独立终端依赖](../terminal/README.md)。

固定源码、Bun PTY、包解析、依赖版本和锁文件见 [Web 依赖](../web/README.md)。

## code 派发与执行

`src/chat/extension.ts` 提供 `dispatch_code` 工具、`/workbot` 和 `/workbot-web` 命令。用户每次确认中心 Issue 和完整目标集合后，chat 通过 `src/tasks/collaboration.ts` 在控制项目创建 API Pipeline，传入 `MODE=code`、`WORKBOT_ISSUE` 和 `WORKBOT_TARGETS`。

当前确认规则由角色工作约定和工具描述指导模型遵守；`dispatch_code` 只校验 Issue、目标和控制项目，不独立核验当前用户消息，也不是强制审批系统。部署面向可信团队；扩大访问范围前需先补足确定性确认和权限控制。

`src/code/run.ts` 的执行流程：

1. 校验目标输入为 1–10 个不同项目的字符串数组，再初始化 Pi 配置和预拉取项目。
2. 读取中心 Issue 当前正文和最近 100 条讨论，Pi 可用 glab 继续查询更早上下文。
3. 准备 1–10 个目标仓库，查询明确指定的 MR 或任务分支对应的 MR。
4. 首次创建 `work/<控制项目ID>-<Issue IID>` 分支；继续任务时检出原 MR 源分支。
5. 启动一个 Pi `--print` 会话，按角色约定编码、检查、提交、推送并创建或更新 MR。
6. 将最终摘要或执行失败信息写回原 Issue，并关联 Pipeline。

取得有效 Issue 引用后，目标输入校验、初始化和执行阶段的失败、取消均尝试回写 Issue；评论失败仅输出诊断，Job 保留原始错误。MR 已关闭、合并、结果不唯一或源分支丢失时停止准备并报告。派发结果未知时由用户核对 GitLab；已产生的跨项目成果逐项确认。Review 由用户请求 chat 执行，最终合并由人工完成。Pi 进程正常结束只表示本次执行结束，不等于全部需求完成；通知要求核对逐项目结果，不解析模型措辞来推断交付状态。

## 部署与记录

默认分支 push 通过检查后构建角色镜像，再由 `pi-workbot-chat` Runner 执行 Compose 部署 chat。部署 Job 使用 `resource_group: chat` 串行化，等待渠道健康检查；失败时输出状态和日志并返回失败。过时部署保护由 GitLab 项目设置控制。API code 流水线使用执行 ref 对应提交的 code 镜像。并发和资源由 Runner 与部署配置控制，凭证按 `chat` / `code` environment 分别提供。

chat 仅持久化会话，工作区和在线配置使用容器本地文件系统；code 使用独立 Job 工作区。容器删除后临时状态随之丢弃，正式成果保存在 GitLab：

| 内容                                         | 保存位置                           |
| -------------------------------------------- | ---------------------------------- |
| 需求、Plan、重要讨论、执行反馈和 Review 结论 | 控制项目 Issue                     |
| 代码、MR、检查结果和执行日志                 | 目标仓库、MR、Pipeline / Job       |
| chat 原始会话                                | `chat-sessions` 命名卷，重建后保留 |
| chat 在线设置和工作文件                      | chat 容器，重建后丢弃              |
| code 原始会话和工作文件                      | code Job 内部                      |

IM 的 `/new`（或 `/clear`）、`/abort` 管理当前会话，独立 code Job 通过 GitLab 取消。
