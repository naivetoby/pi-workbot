# 使用说明

本文面向 GitLab 团队部署。仅体验 chat/Web 请先看 [独立部署](../deploy/README.md)。

## 部署准备

### 1. 配置工作区

按 [环境配置](环境配置.md) 调整 `configs/`：

- `chat/settings.json`：模型、插件和可选的 IM 渠道，详见 [IM 配置](环境配置.md#im-配置)。
- `chat/AGENTS.md`、`code/AGENTS.md`：角色工作约定。
- `shared/`：模型端点、MCP 和 Skills。
- `projects.json`：启动时预拉取的项目。省略 `branch` 时使用 GitLab 默认分支。

```json
[{ "project": "your-group/backend" }, { "project": "your-group/frontend" }]
```

项目克隆到 `/workspace/repos/<完整项目路径>`。code 会按本次目标补充克隆项目，控制项目也可作为目标。

### 2. 准备 GitLab 和 Runner

仓库提供 `.gitlab-ci.example.yml` 示例。需要 GitLab 部署和 code Job 时，在仓库根目录复制为正式配置，按需调整并提交：

```sh
cp .gitlab-ci.example.yml .gitlab-ci.yml
```

为专用服务账号 `pi-workbot` 配置授权项目的 Developer 权限，以及控制项目的 Pipeline 执行和变量传递权限。分支保护、变量可用范围和 Runner 并发由维护者在 GitLab 配置。

| Runner tag         | 镜像                                                    | 职责                     |
| ------------------ | ------------------------------------------------------- | ------------------------ |
| `pi-workbot-build` | `WORKBOT_CI_IMAGE`（默认 `docker:cli`）                 | 构建并发布角色镜像       |
| `pi-workbot-chat`  | `WORKBOT_CI_IMAGE`                                      | 在部署服务器执行 Compose |
| `pi-workbot-code`  | 检查使用 `WORKBOT_BASE_IMAGE`，编码使用本项目 code 镜像 | 检查、smoke 和 code Job  |

构建和部署 Runner 使用 Docker executor，并挂载本机 Docker socket。Docker Compose 需要支持 `up --wait --wait-timeout`。镜像基线见 `.gitlab-ci.example.yml` 和 `Dockerfile`；Runner tag 可通过 CI 变量 `WORKBOT_BUILD_RUNNER`、`WORKBOT_CHAT_RUNNER`、`WORKBOT_CODE_RUNNER` 调整。`WORKBOT_BASE_IMAGE` 默认 `naivetoby/pi-workbot-dev:latest`，用于检查镜像和 Docker 构建底座；`WORKBOT_CI_IMAGE` 需包含 Docker CLI 与 Compose 插件。这些变量设为所有 environment 可用。

在 GitLab 项目 CI/CD 设置中启用 **Prevent outdated deployment jobs（阻止过时部署任务）**。`resource_group: chat` 只保证不同时部署，不能单独保证按提交先后部署；项目设置需要维护者核实。

### 3. 配置运行变量

在 GitLab CI/CD Variables 中按 environment 设置凭证：

| 变量                                            | environment       | 用途                                                    |
| ----------------------------------------------- | ----------------- | ------------------------------------------------------- |
| `GITLAB_TOKEN`                                  | `chat`、`code`    | 服务账号访问令牌                                        |
| `GITLAB_HOST`                                   | `code`            | GitLab 实例；chat 由 Compose 使用 `CI_SERVER_HOST` 提供 |
| `OPENAI_RELAY_BASE_URL`、`OPENAI_RELAY_API_KEY` | `chat`            | chat 默认中转模型地址（含 `/v1`）与凭证                 |
| `DEEPSEEK_API_KEY`                              | `code`；chat 按需 | code 默认模型凭证                                       |
| `FEISHU_APP_ID`、`FEISHU_APP_SECRET`            | `chat`            | 飞书应用凭证                                            |
| `WECOM_BOT_ID`、`WECOM_BOT_SECRET`              | `chat`            | 企微机器人凭证                                          |
| `WECOM_BOT_URL`                                 | `chat`、`notice`  | 可选，企业微信群机器人通知 Webhook                      |
| `PI_WEB_PASSWORD`、`PI_WEB_ALLOWED_HOSTS`       | `chat`            | Web 认证和允许的访问主机                                |
| `WORKBOT_WEB_BIND`                              | `chat`            | 宿主 Web 监听地址，默认 `127.0.0.1`                     |
| `WORKBOT_WEB_AUTOSTART`                         | `chat`            | 设为 `1` 时随 chat 启动 Web，默认不自动开启             |
| `WORKBOT_TUI_ENABLED`                           | `chat`            | 设为 `1` 启用独立终端；必须同时设置 `PI_WEB_PASSWORD`   |
| `WORKBOT_CODE_REF`                              | `chat`            | code 执行 ref，默认控制项目的默认分支                   |

凭证按实际使用的服务提供，仅在运行时注入。IM 按完整凭证自动启用，详见 [IM 配置](环境配置.md#im-配置)。新增模型或 MCP 凭证时，在对应 environment 提供变量，并在 Compose `environment` 中显式传入 chat 所需变量。

### 4. 发布和部署

提交配置并推送默认分支，流水线依次执行：

1. `bun run check` 和 `bun run smoke`；相关变更增加 `check:assets`、`check:web`、Linux Pi/lens 验收 Job `check-lens` 和终端验收 Job `check-tui`。这些检查也在 MR 和普通分支执行，触发路径以 CI `rules:changes` 为准。
2. 构建并发布 `$CI_REGISTRY_IMAGE/code:$CI_COMMIT_SHORT_SHA` 和 `$CI_REGISTRY_IMAGE/chat:$CI_COMMIT_SHORT_SHA`。
3. `deploy-chat` 在专用 Runner 上串行执行 `docker compose pull chat` 和 `docker compose up --no-build --wait --wait-timeout 420 chat`。渠道未就绪时部署失败，打印容器状态与最近日志，不发成功通知。

Compose 从 `CI_PROJECT_PATH` 获取控制项目，从 CI 变量获取镜像和 GitLab 实例。MR 与其他分支执行检查；API code 流水线执行 code Job。

容器首次启动时复制 Pi 配置、准备项目并启动 chat 宿主。健康检查、故障诊断、回滚及会话备份恢复见 [运维说明](运维.md)。

## 需求与编码

正式项目编码始终通过 code Job。在 IM 或 Web 中讨论需求，让 Pi 用 glab 创建控制项目 Issue，持续维护需求、Plan、约束和验收条件。准备编码时，当前用户单独发送：

```text
执行 your-group/pi-workbot#12 your-group/backend your-group/frontend
```

Pi 根据确认调用 `dispatch_code`。Web 中可以直接使用：

```text
/workbot your-group/pi-workbot#12 your-group/backend your-group/frontend
```

一次派发对应一个 code Job、一个 Pi 会话，支持 1–10 个目标项目。code 启动时读取 Issue 当前内容和讨论，准备任务分支，按项目约定编码、检查、提交、普通 push 并用 glab 创建或更新 MR。结果回写原 Issue，主要验证由目标项目的 MR CI 承担。

初始化中的项目访问、克隆，以及后续执行失败或取消时，Job 尝试将原因和 Pipeline 链接写回原 Issue。评论失败时在 Job 日志输出诊断，并保留原始失败结果。

Job 成功和“编码执行结束”通知仅表示进程正常结束，可能仍有无变更、阻塞或部分交付。请先核对 Issue 中的逐项目结果，再请原 Plan 会话 Review 实际 MR、相关源码和 CI 结果。需要修改时更新 Issue，再确认执行；最终由人工审核合并。

### 继续 MR

目标写成 `your-group/backend!7` 可指定 MR。省略 MR 编号时，code 查找任务分支 `work/<控制项目ID>-<Issue IID>` 对应的 MR，并继续其源分支。MR 已关闭、合并、源分支丢失或查询结果不唯一时，先核对 GitLab 状态并讨论处理方式。

派发失败或结果未知时，先查看 GitLab Pipeline 和 MR，再决定下一步。取消 code Job 使用 GitLab；IM 的 `/new`（或 `/clear`）、`/abort` 只作用于当前会话。`/clear` 与 `/new` 都由渠道层处理：取消当前任务、丢弃排队消息并删除当前聊天的会话文件，下一条消息开启新会话；不会清空其他聊天。

### code 执行条件

- 执行 ref 对应提交的 code 镜像已发布。
- `code` environment 已配置 GitLab 和模型凭证。
- API 流水线使用 `MODE=code`、`WORKBOT_ISSUE` 和 `WORKBOT_TARGETS`（目标引用的 JSON 数组）。
- 服务账号可在所选 ref 创建 Pipeline、传递变量，并访问目标项目。

## 按需使用 Web

Web 默认按需开启；设置 `WORKBOT_WEB_AUTOSTART=1` 可随 chat 启动。手动管理命令：

```sh
docker compose exec chat bun src/cli.ts web start
docker compose exec chat bun src/cli.ts web status
docker compose exec chat bun src/cli.ts web stop
```

也可在 IM 中请 Pi 执行脚本，或在 Web 使用 `/workbot-web start|stop|status`。TUI 不持有 Web 密码，仅用于查询或停止 Web；停止后由管理员或 IM 重新启动。

Web 用于讨论、Review 和环境试验。新会话默认目录为 `/workspace`，跟随 `WORKBOT_WORKSPACE`；本地运行使用配置的本地工作区。项目目录见工作区根目录 `AGENTS.md`。

默认宿主地址为 `127.0.0.1:30141`，远程访问方式由维护者配置。启动后访问页面或检查 `/runtime/web.log` 确认就绪；`status` 检查进程是否存活。

Web 与 IM 共用 Pi 设置和会话存储，会话默认在 Web 侧栏归入同一工作区，聊天上下文仍相互隔离：

- **IM 会话**：仅供查看，回复请回到对应的飞书或企业微信聊天；不支持从 Web 启动独立 TUI。
- **Web 自建会话**：可正常交互。打开已保存会话时，先在后台检查 TUI 状态，再显示聊天区或只读记录；检查失败时可重试。
- **共享边界**：只读视图用于防止误操作，不限制通用会话 API 的访问权限。各会话共享项目文件，编辑和提交时需相互协调。

在线配置按 Pi 的加载规则生效。试验、配置固化与重建验证见 [云端环境迭代](环境迭代.md)。

### 独立 Pi TUI

默认关闭。设置 `WORKBOT_TUI_ENABLED=1` 和非空 `PI_WEB_PASSWORD` 后重新部署；本地运行需重启 Web。在已保存的普通 Web 会话中点击「打开 TUI ↗」，即可在新标签页使用 Pi。启动前需结束 GUI 任务及后台工作；IM 和子代理会话不支持此入口。

- **登录**：页面、资源和 WebSocket 共用 pi-web 认证，无额外公开端口或终端密码。当前使用共享密码，不提供逐用户会话权限；注销只阻止新连接，不立即切断已有 WebSocket。
- **连接与退出**：同一会话复用同一个 Pi 进程。关闭标签页或停止 Web 不结束 Pi，刷新可重新连接；输入为空时 `Ctrl+D` 退出，不留下 shell。退出后需回 GUI 重新打开。
- **会话边界**：受管 TUI 固定启动时的会话，阻止 `/new`、`/resume` 切换和 `/fork`、`/clone` 分叉；请先退出 TUI，再在 GUI 操作其他会话。文件内的 `/tree` 导航和 `/reload` 保留原生行为，此限制不影响 IM 或独立启动的 Pi。
- **GUI 只读**：TUI 存在时，聊天区只显示记录，不启动 GUI SDK；进入、返回焦点及每 10 秒检查状态，退出后刷新记录并恢复 GUI。这不是写锁，不要从其他标签页、API 或 CLI 同时修改、删除该会话。
- **工具与配置**：TUI 使用同一套 Pi 配置，不传入 GUI 的工具预设。保留 Pi 原生续接行为：可能恢复历史消息中的工具集合，而非每次重置为 `defaultTools`。GUI 写入共享 `settings.json` 的修改仍按 Pi 规则生效。新建 TUI 使用当前 Web 的运行环境，不继承旧 tmux 服务的凭证；保活进程仍使用原环境，更新凭证或终端适配代码后需退出并重新打开。
- **复制**：`/copy` 写入浏览器剪贴板，需要页面有焦点、允许剪贴板访问，并使用 HTTPS 或 localhost。权限拒绝或文本超过 Pi 的 OSC 52 长度上限时可能失败，“Copied”提示不能代替实际粘贴检查。
- **资源**：每个会话占用一个 Pi 进程，无自动过期或数量上限。容器停止或重建会结束进程，仅保留已落盘的会话；不同会话仍需协调工作区文件修改。

外部反向代理需支持 WebSocket，远程访问使用 HTTPS。

管理员清理终端（会中断运行任务）：

```sh
docker compose exec chat tmux -S /runtime/tui.sock list-sessions
docker compose exec chat tmux -S /runtime/tui.sock kill-session -t '=pi-<会话摘要>'
```

关闭 TUI 功能前，先退出所有 Pi TUI 或清理相应 tmux 会话，避免存活的终端与 GUI 同时写入。

## 本地开发

需要 Bun `>=1.4.2`，项目和 Web 使用 Pi `1.6.0`。

```sh
bun install --frozen-lockfile --ignore-scripts
bun run check
bun run smoke
bun run check:assets
bun run check:web
```

独立 TUI 的依赖安装、`check:tui` 和浏览器验收见 [独立终端依赖](../terminal/README.md#验证与更新)。

| 命令           | 检查内容                                                                             |
| -------------- | ------------------------------------------------------------------------------------ |
| `check`        | 格式、lint、TypeScript、单元与本机集成测试                                           |
| `smoke`        | 临时配置、空项目清单下启动真实 Pi RPC，检查配置和扩展加载                            |
| `check:assets` | 冻结安装两个角色插件并执行角色资产 smoke                                             |
| `test:web`     | 准备固定 Web 源码与依赖，实际执行 Workbot 自维护补丁测试                             |
| `build:web`    | 校验并解压本地源码包、应用补丁、冻结安装、执行补丁测试并生成 Bun 生产构建            |
| `check:web`    | 生产构建（包含补丁测试）及 `smoke --web`                                             |
| `check:tui`    | 准备终端页面、生产 Web 构建及真实 TUI 认证与生命周期检查                             |
| `smoke --web`  | 额外检查生产 Web 的默认工作区、IM 会话读取、HTML 导出、设置写入、MCP 页面和 PTY 输出 |

检查实际角色资产：

```sh
bun run prepare:pi configs/chat
bun run prepare:pi configs/code
bun run smoke:chat
bun run smoke:code
```

`prepare:pi` 核对角色 settings 与安装清单，按锁文件冻结安装，可能需要联网下载依赖，但不自动更新版本。只有显式 `--update-lock` 才更新安装清单和锁文件，步骤见 [环境配置](环境配置.md#构建与资产检查)。角色 smoke 在临时 HOME、空项目清单和清空的凭证环境下检查插件、共享模型/MCP、Skills 与工具加载；镜像构建时也会执行。

Linux 角色镜像使用预装语言环境执行集成验收：

```sh
docker build --pull --provenance=false --target code .
docker build --pull --provenance=false --target chat-assets .
```

两个阶段分别运行 `bun run smoke:lens <角色>`，在 Docker 禁网构建层隔离 HOME 和凭证，验证 TS/Python/Java/JSON/YAML/CSS/C++ 的错误与修复、HTML 符号及会话退出。诊断限时 300 秒，关闭宽限 15 秒，Pi `--print /lens-tools` 退出检查限时 60 秒。chat 验收子进程使用预装工具，运行时支持按需安装。

本地集成测试使用模拟平台和模型，GitLab API 使用命令替身，关键分支准备另用真实本地 bare Git 仓库验证。测试结构和维护原则见 [仓库开发约定](../AGENTS.md)；测试修改全局环境和 mock，保持串行执行。

上线前还需在部署环境验证 Linux 镜像、真实 IM、模型及 GitLab 协作流程。变更类型与验收对应关系见 [环境迭代](环境迭代.md#变更验收清单)。
