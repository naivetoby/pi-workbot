# 运维说明

Workbot 面向可信团队共用的研发环境，不提供租户隔离。模型、插件及工具可以访问容器内提供的凭证和网络；准入范围、GitLab 权限、分支保护、Web 认证与网络边界由维护者负责。

以下命令在部署服务器、项目 Compose 目录执行，需要 Docker 权限及与部署 Job 相同的镜像变量、运行凭证。不要将凭证写入命令历史或提交到仓库，也不要将展开后的 `docker compose config` 输出到公共日志。

## 部署就绪与故障定位

部署由 `resource_group: chat` 串行化，Compose 最多等待 420 秒完成宿主初始化及全部启用渠道的双向连接；无 IM 时，仅检查宿主初始化。维护者还应在 GitLab 启用阻止过时部署任务；串行不等于按版本先后执行。

```sh
docker compose ps --all chat
docker compose logs --no-color --tail 100 chat
docker compose exec chat bun src/cli.ts web status
docker compose cp chat:/runtime/web.log ./web-diagnostic.log
```

- **渠道不健康或未启动**：检查 [IM 凭证](环境配置.md#im-配置)、应用准入及网络，再检查项目访问和初始化日志。
- **Web 无响应**：`status` 只检查进程存活；另检查 Web 日志、监听地址、认证和实际页面响应。
- **code 失败或结果未知**：以 Pipeline、Issue、分支和 MR 实际状态为准；可能已有部分成果，不自动重试。IM `/abort` 不会取消 code Job。
- **Job 成功但任务未完成**：执行进程成功不代表需求验收成功，核对逐项目摘要、MR 和项目 CI。

健康检查不验证 Web 页面、模型或 GitLab 业务链路，仍需实际验收。Compose 的 `restart: unless-stopped` 处理进程退出，不会仅因 unhealthy 自动重启；应由部署监控关注 unhealthy、重启次数、磁盘及卷使用量，不以无限重启替代诊断。

容器 stdout 已配置轮转；`/runtime/web.log` 是独立文件，不受 Docker 日志轮转控制。长期启用 Web 时需监控该文件大小，按维护窗口停止 Web、归档必要日志后截断或纳入部署服务器的轮转策略。诊断日志和会话可能含敏感内容，限制访问、脱敏后再分享。

## lens 工具依赖

`pi-workbot-dev:latest` 提供 Bun、Node.js、Python、Java/Maven、语言服务器和检查器。Bun 运行 Workbot，Node.js 运行 JS 工具；Java 由 SDKMAN 管理，默认使用 JDK 21，JDT LS 使用 JDK 25。角色以 `vscode` 用户运行，并在禁网构建层验证 Pi/lens 诊断和退出。

预装工具以底座镜像的验收记录为准，业务项目提供自身依赖、专用 SDK 和编译测试命令。镜像与会话卷权限验收见 [环境基线与更新](环境迭代.md#环境基线与更新)。

- **chat**：默认允许 lens 按需安装缺失工具；不是定期升级，仍受 Bun 兼容性、权限和网络条件限制。在线安装随容器重建清空，不会自动同步给 code。
- **code**：镜像设置 `PI_LENS_DISABLE_LSP_INSTALL=1` 和 `PI_LENS_DISABLE_TOOL_INSTALL=1`，保留已有工具的检查，禁止 lens 自动安装依赖。缺失工具对应的检查可能不可用或不完整，不能当作检查通过。

这两个开关仅约束 lens 的安装流程，不限制 Agent 使用普通命令安装业务项目依赖，也不是网络隔离措施。更新预装工具后，先验证底座，再重新构建角色镜像。

## 镜像回滚

1. 暂停派发、协调暂停自动部署，记录故障镜像 tag/digest 与 Pipeline；先保存必要的工作成果和会话备份。
2. 在 Registry 确认上一套通过验收的 chat/code 镜像仍存在。回滚使用已发布镜像，不重新构建旧提交来猜测原环境。
3. 在受控部署环境中，将 `CI_COMMIT_SHORT_SHA` 设为目标镜像的实际 tag，其余变量与凭证沿用部署配置：

   ```sh
   export CI_COMMIT_SHORT_SHA='<已验证的旧镜像 tag>'
   docker compose pull chat
   docker compose up --no-build --wait --wait-timeout 420 chat
   ```

4. 验证 IM、Web 及会话可读；恢复自动部署前在仓库修复或回退问题变更，避免下一次流水线重新覆盖。

chat 重建会丢弃在线设置和工作文件，但保留 `chat-sessions` 卷。旧版本可能无法读取新版本的会话格式；恢复备份时应使用新卷，先在隔离环境验证兼容性，不覆盖正在使用的卷。

chat 回滚不会回滚正在执行的 code Job。需要回退 code 环境时，另将 `WORKBOT_CODE_REF` 指向对应的已发布提交/ref，并确认该提交的 code 镜像可拉取；是否取消现有 Job 由维护者决定。

## 会话备份

持久化卷不是备份。安排保留周期、异机保存和恢复演练；备份包含原始对话、工具调用及可能的敏感数据，应限制权限并按部署要求加密。具体周期由团队的数据保留要求决定。

为得到一致的备份，在维护窗口暂停新消息和 Web 操作后停止 chat。以下通过临时容器读取同一个会话卷，不持久化整个工作区：

```sh
umask 077
BACKUP="/安全备份目录/chat-sessions-$(date +%Y%m%d-%H%M%S).tar.gz"
docker compose stop chat &&
if docker compose run --rm --no-deps -T --entrypoint tar chat \
  -C /runtime/pi/sessions -czf - . > "$BACKUP" && tar -tzf "$BACKUP" > /dev/null; then
  echo '归档已生成并通过可读性检查；仍需恢复演练'
else
  echo '备份失败；不要将此文件标记为可恢复备份' >&2
fi
docker compose start chat
```

检查命令退出状态和归档可读性，并记录备份对应的镜像版本；仅列出归档不能替代完整恢复演练。根据现场情况确认 chat 恢复健康。不要运行 `docker compose down -v`，它会删除会话卷。

## 恢复到新卷

恢复是人工维护操作。先停止 chat、保留并备份当前卷，确认备份来源可信。**不要覆盖现有卷**；创建一个临时 Compose override，将会话卷指向一个新的、未使用过的名字：

```yaml
# restore.compose.yml；替换为本次恢复专用的新名字
volumes:
  chat-sessions:
    name: pi-workbot-chat-sessions-restore-YYYYMMDD
```

确认目标名字尚未被使用后，在保持 chat 停止的状态下解包，再启动服务：

```sh
docker compose -f compose.yml -f restore.compose.yml run --rm --no-deps -T \
  --entrypoint tar chat -C /runtime/pi/sessions -xzf - < "$BACKUP" &&
docker compose -f compose.yml -f restore.compose.yml up \
  --no-build --wait --wait-timeout 420 chat
```

验证 Web/IM 历史、会话接续及文件权限。验证通过后，将选定卷名固化到正式部署配置，否则下一次常规部署会重新使用原卷；未通过则恢复原 Compose 配置和原镜像，原卷仍保留。旧卷删除须另行确认，不属于恢复步骤。
