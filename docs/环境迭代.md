# 云端环境迭代

维护者在 Web 中试验模型、插件、Skills、提示词、工具链和安全策略，将有效配置通过 PR 固化到仓库与镜像。凭证通过运行环境提供。

一次围绕一个明确目标迭代，例如升级一个插件或增加 Java 编译环境。先确定验证样例，再将选用版本、关键配置、验证结果和待解决问题记录到 Issue。

## 试验与保存位置

| 内容                           | 云端试验位置                                     | 长期保存位置                                               |
| ------------------------------ | ------------------------------------------------ | ---------------------------------------------------------- |
| 模型、思考强度、插件与工具设置 | `/runtime/pi/settings.json`、Web 设置            | `configs/chat/settings.json`、`configs/code/settings.json` |
| 模型端点与 MCP                 | `/runtime/pi/models.json`、`mcp.json`            | `configs/shared/`，角色差异放对应角色目录                  |
| 研发约定与提示词               | `/runtime/pi/AGENTS.md`、系统提示词和 `prompts/` | 角色目录或共享目录中的原生文件                             |
| Skills、扩展与安全策略配置     | `/runtime/pi/skills/`、`extensions/` 及插件配置  | `configs/shared/` 或角色目录                               |
| 编译器、SDK、构建和测试工具    | 云端终端中的必要验证                             | 基础镜像项目或本项目 `Dockerfile`                          |
| 凭证                           | GitLab environment、Pi 运行时凭证                | GitLab `chat` / `code` environment                         |

表中运行路径为容器默认值。运行中的程序位于 `/opt/workbot`，正式变更使用 `/workspace/repos/<完整项目路径>` 中的仓库副本。

## 按需验证

- **模型**：用实际需求讨论、Review 和工具调用样例比较效果、速度与成本。模型端点、默认模型和思考强度分别按 Pi 原生配置调整。
- **插件**：显式安装或升级选定版本，再验证工具实际可用。运行进程使用离线资源发现；直接修改包声明后，需要准备对应依赖并按入口加载机制 reload 或重启。
- **Skills 与提示词**：观察真实任务中的触发、指令遵循和输出质量。更新上游 Skills 时同步维护 `skills-source.json`、来源提交与许可证。
- **编译与测试环境**：按近期项目需要逐步增加工具链，验证版本、命令、依赖安装及必要的构建或测试，再固化到镜像。
- **安全策略**：用临时路径和虚构敏感值验证禁读、工具权限、输出脱敏等规则，检查 read、bash、MCP、子代理和日志等相关入口。

提示词表达工作约定，权限插件约束其覆盖的调用链；真正禁止访问的文件和凭证，需要进程权限、容器可见范围和凭证注入范围配合。记录验证过的保护范围，再决定配置如何推广到两个角色。

## 环境基线与更新

- **插件**：先修改角色 `settings.json`，再运行 `prepare:pi <角色目录> --update-lock`，审查并提交角色 `npm/package.json`、`npm/bun.lock`。普通构建冻结安装，不在发布时临时追随传递依赖更新。
- **基础镜像**：`Dockerfile` 和 CI 使用 `pi-workbot-dev:latest`，默认底座为 `naivetoby/pi-workbot-dev:latest`，通过 `WORKBOT_BASE_IMAGE` 覆盖；CI 工具镜像由 `WORKBOT_CI_IMAGE` 指定，默认 `docker:cli`。底座仓库维护 Dev Containers Base、官方语言 Features 和工具清单，冻结 Features/npm 锁文件并验证通用工具；版本升级显式更新配置与锁文件。
- **角色集成**：Workbot 使用自身 Pi 与锁定插件执行 `smoke:lens`；`check-lens` 构建禁网的 `code` 和 `chat-assets` 阶段，chat 成品组合已验证角色资产与 Web/TUI。CI 构建通过 `--pull` 拉取底座。
- **保留与回退**：角色镜像按提交 SHA 发布，在 Registry 保留当前及上一套通过验收的角色镜像，避免清理策略回收回滚所需内容。`latest` 会变化，同一源码重新构建不保证得到原环境；回滚使用已发布的角色镜像，不依赖重新构建旧提交。回滚和会话恢复见 [运维说明](运维.md)。

### 镜像验收

底座在 Linux Docker/BuildKit 环境构建，验收记录包含实际工具版本和 Features 锁摘要。角色构建使用已发布底座，Workbot Runner 与 `CI_JOB_TOKEN` 需具备镜像拉取权限。

- **工具与集成**：验证角色 Pi/lens、Web/TUI、真实项目编译和 IM/模型交互，以及 code 退出和 Issue 回写。
- **用户与存储**：按实际 UID/GID 核对 HOME 和 `/runtime/pi/sessions` 权限，使用会话备份副本验证读写与恢复。
- **发布顺序**：底座、角色镜像、chat 部署；回滚使用 Registry 中保留的已验收角色镜像。

`deploy/` 的构建与更新方式见 [独立部署](../deploy/README.md#镜像构建与维护)。

## 固化与发布

1. **整理配置差异**：从运行目录选取有效的非敏感配置，保留环境变量引用、固定版本和可重建路径。按仓库源配置组织文件，运行时 bridge 入口由初始化脚本注入。
2. **确定角色范围**：共用资产放 `configs/shared/`；模型、插件和策略按实际需要分别更新 chat/code。chat 的在线调整只影响当前 chat，code 使用其镜像中的配置。
3. **检查提交内容**：密钥、OAuth 状态、会话、缓存、`npm/node_modules/` 安装结果和临时工作文件留在运行环境中；角色 `npm/package.json`、`npm/bun.lock` 是需要提交的非敏感构建输入。新增凭证引用同步配置 GitLab environment 与 Compose 变量。
4. **验证并提交 PR**：按改动运行检查，人工 Review 后合并、构建并发布镜像。基础工具镜像有改动时先发布并验证底座，再构建 Workbot 角色镜像。
5. **重建验证**：确认新容器的默认模型、插件、Skills 和工具链实际生效。共享改动分别验证 chat/code，再按需验证 IM、Web 与 GitLab 协作流程。

验证命令见 [使用说明](使用.md#本地开发)。共享 Pi 资源分别执行 chat/code 资产检查；Web 改动增加生产构建和 Web smoke；镜像与系统工具改动在 Linux 部署环境验证。

**容器仍可丢弃，重要成果需要保存。** 重建前，将结论、配置和代码保存到对应仓库或部署配置中。后续试验从新的环境基线继续。
